# Running PaSh on this Mac — the `pash` VM

**Written 5 October 2026**, updated the same day with the verification results. Phase 0 of
[`../tasks/012_pash_downstream_study.md`](../tasks/012_pash_downstream_study.md). PaSh is the
compiler that rewrites a shell script so its pipelines run in parallel; the downstream study feeds
it annotations from v1 and from v2 and checks what it does with them.

This is the counterpart of [`caruca_v1 pipeline instructions.md`](caruca_v1%20pipeline%20instructions.md),
which covers v1's own pipeline. **Two separate virtual machines, on purpose** — see §2.

---

## 1. The headline finding, before any instructions

**No version of PaSh since 8 September 2022 can read JSON annotation files, including the version
the Caruca paper ran.** This was the single biggest unknown in the study's plan, and it is now
settled:

| Evidence | Where |
|---|---|
| JSON annotations were deleted from PaSh | commit `92364f6a`, 2022-09-08, *"Remove old annotations and move them to annotations repository"* |
| Modern PaSh reads annotations as **Python classes** from the `pash-annotations` package | `pyproject.toml` declares `pash-annotations~=0.2.4`; `src/pash/compiler/annotations_utils/util_cmd_invocations.py` calls `get_input_output_info_from_cmd_invocation` and `get_parallelizability_info_from_cmd_invocation` |
| There is no JSON reader anywhere in `pash_annotations` | the only JSON it touches is `command_flag_option_info/data/*.json`, which is the flag-parsing table (which flags take a value), not a parallelizability annotation |
| **The paper's own run could not have read JSON either** | the revision current at the paper's CloudLab run, `0d0a563b` (2024-11-18), already declared `pash-annotations==0.2.2` in `requirements.txt` |

**What this decides.** The study's pinning rule was "the newest revision that builds *and* reads
JSON; failing that, weigh a code-generating adapter against pinning an older revision, preferring
whichever is closest to the paper's November 2024 run." There is no JSON-reading revision worth
having — JSON support ended two years *before* the paper's run — so pinning an old revision would
move us further from the paper, not closer. **Decision: pin a modern revision and have the adapter
emit Python classes.**

**What this opens.** Caruca's committed annotations are JSON (`eval/pash-annotations/*.json` in
v1's tree). A November 2024 PaSh could not consume them. So the paper's "we replace its built-in
specifications with the ones generated by Caruca and run its benchmark suite" step used either a
much older PaSh, or an uncommitted conversion, or something else. This is question 2 in task 012
§11 and it is now much sharper than when it was written.

### 1.1 What an annotation looks like in this format

Not a class label. A generator is imperative Python that **appends parallelizers**, each pairing a
splitting strategy with an aggregator (the function that merges the pieces' output). Example, the
whole of `ParallelizabilityInfoGeneratorUniq`:

```python
def generate_info(self) -> None:
    if not self.does_flag_option_list_contain_at_least_one_of(["-d", "-D", "--all-repeated"]):
        if self.does_flag_option_list_contain_at_least_one_of(["-c"]):
            aggregator_spec = make_aggregator_spec_adj_lines_func_from_string_representation(
                cmd_inv_as_str='PLACEHOLDER:uniq_merge_count_uniq', is_implemented=False)
            self.append_to_parallelizer_list(make_parallelizer_consec_chunks(aggregator_spec=aggregator_spec))
            self.append_to_parallelizer_list(make_parallelizer_round_robin(aggregator_spec=aggregator_spec))
        else:
            self.append_to_parallelizer_list_cc_seq_adjs()
            self.append_to_parallelizer_list_rr_seq_adjs()
```

Consequences for the study's adapter (Phase 1):

- Caruca's four classes map onto *actions*, not a field: `stateless` → append a parallelizer with
  a concatenating aggregator; `pure` → append one with a specific aggregator Caruca cannot
  synthesise; `non-pure` and `side-effectful` → **append nothing**.
- **There is no "default case" to supply.** Appending nothing *is* the conservative default, so the
  question the task doc raised ("does PaSh require a default case?") does not arise.
- **What PaSh does with an unannotated command**: the dispatch looks the name up in
  `DICT_CMD_NAME_TO_REPRESENTATION_IN_MODULE_NAMES`, tries to import a class, and on any exception
  returns `None`. That is the "no annotation" control arm, and it needs no special setup.
- The adapter is therefore a **code generator**, and the parity study's class-agreement figures do
  not carry over to this format unchanged.

### 1.2 How little the stock annotation set covers our commands

`pash-annotations` 0.2.4, against the study's nine commands:

| Command | In the dispatch table | Input/output generator | **Parallelizability generator** |
|---|---|---|---|
| `uniq` | yes | yes | **yes** |
| `cat` | yes | yes | no |
| `tail` | yes | yes | no |
| `tee` | yes | yes | no |
| `rm` | yes | yes | no |
| `wc` | **no** | file exists but is unreachable | no |
| `pwd`, `sha256sum`, `tac` | no | no | no |

So of the nine, **only `uniq` has a hand-written parallelizability annotation in modern PaSh.** The
status-quo comparison arm is far thinner than the plan assumed, and stock PaSh will not parallelize
`cat`, `tail`, `tee` or `wc` at all. Note also that `InputOutputInfoGeneratorWc` and
`...GeneratorAwk` exist as files but their commands are absent from the dispatch table, so they can
never be reached — worth reporting.

The 15 commands that do have parallelizability generators: `grep`, `sed`, `sort`, `tr`, `cut`,
`col`, `uniq`, `xargs`, plus the benchmark-specific `CustomSort`, `CustomTr`, `SetDiff`,
`AltBigramsAux`, `BigramsAux`, `TestOne`, `TestTwo`.

## 2. The VM, and why it is a second one

| | `caruca` VM | `pash` VM |
|---|---|---|
| Purpose | runs v1's pipeline (tracing, annotating) | runs PaSh |
| Mac home mount | **writable** | **read-only** |
| Created | 2026-09-03 | 2026-10-05 |

Two reasons for a second VM. The `caruca` VM produces every v1-side measurement in the project, so
a PaSh install must not perturb it. And the downstream matrix runs `rm` and `tee` under annotations
that may be mistranslated, so **the Mac filesystem is mounted read-only here** and every script
runs in a throwaway directory on the VM's own disk. Verified: `touch` against the mounted Mac home
fails with `Read-only file system`.

```sh
limactl create --name=pash --vm-type=vz --cpus=8 --memory=8 --disk=40 --tty=false template:ubuntu-24.04
limactl start pash
limactl shell pash
```

Lima's default mount is read-only, so no `--mount-writable` — that flag is what makes the `caruca`
VM writable, and it must not be used here.

**Baseline, recorded because the study depends on it:**

| | |
|---|---|
| OS | Ubuntu 24.04.4 LTS, aarch64 |
| **coreutils** | **9.4 — identical to the `caruca` VM** |
| Python | 3.12.3 |
| CPUs / memory / disk | 8 / 8 GiB / 40 GiB (36 GiB free after install) |
| Guest home | `/home/tirandagan.guest` (**not** the mounted Mac home — same trap as the `caruca` VM) |

The coreutils match is a precondition, not a detail: an annotation derived by observing coreutils
9.4 has to be tested against coreutils 9.4, or a version difference looks like an annotation error.

## 3. Installing PaSh

```sh
limactl shell pash
git clone https://github.com/binpash/pash.git ~/pash
cd ~/pash && git checkout 42a8b87          # pinned; see §4
sudo apt install -y python3.12-venv        # NOT in PaSh's own dependency list — see below
./scripts/distro-deps.sh                   # Ubuntu packages, via sudo
./scripts/setup-pash.sh                    # venv at ./python_pkgs + pip install -e .
```

**One defect in PaSh's installer, on Ubuntu 24.04.** `scripts/distro-deps.sh` installs
`python3-pip` and `python3-setuptools` but **not** `python3-venv`, and `scripts/setup-pash.sh`'s
first action is `python3 -m venv`. It fails with *"ensurepip is not available"*. Install
`python3.12-venv` first. Worth reporting upstream.

Afterwards:

```sh
export PASH_TOP=~/pash/src/pash                  # note: src/pash, not the repo root
export PATH="$HOME/pash/python_pkgs/bin:$PATH"
pash script.sh
```

`PASH_TOP` points at `src/pash` in this layout, and the entry point is `pash`, not `pa.sh`. Older
documentation (including v1's vendored copy of PaSh's benchmark README) says otherwise.

### 3.1 Benchmark scripts and their inputs

The suites live in `~/pash/evaluation/benchmarks/`. Each has an `input/setup.sh`, and **`--small`
fetches small inputs** instead of the multi-gigabyte ones:

```sh
cd ~/pash/evaluation/benchmarks/oneliners && ./input/setup.sh --small
```

### 3.2 The flags the study needs

All present on `pash`:

| Flag | Use in the study |
|---|---|
| `-w`, `--width` | parallelism factor. **The default is 2 here**, not 8: it is `cpus//8` only when there are ≥16 cores, else 2. Always pass it explicitly |
| `--r_split` | round-robin splitting instead of consecutive chunks. The study runs both, because a wrong annotation can surface under one and not the other |
| `-d`, `--debug`, `--log_file` | where the compiler's decisions are written |
| `--graphviz`, `--graphviz_dir` | dumps the dataflow graph — the most direct way to see what became a parallel node |
| `--dry_run_compiler` | compile without executing |
| `--assert_all_regions_parallelizable` | **do not use alone — it passes vacuously.** See §3.3 |
| `--output_time` | per-run timing |

### 3.3 Reading the decision — harder than it looks, and not fully solved

Measured 2026-10-05, and the first two attempts were wrong, so the record matters:

- **`--assert_all_regions_parallelizable` is vacuously satisfied when PaSh never attempts a
  region.** `cat in.txt | sort | uniq -d` exits 0 under it, yet nothing was parallelized. It does
  report a real count when PaSh *tries* and fails: `cat in.txt | sha256sum` exits 1 with
  `Not all regions were parallelizable (0/1 parallelized)`. So a pass means "no region failed",
  not "something was parallelized". Used alone it would silently score every unparallelized run
  as a success.
- **`-p` / `--output_optimized` writes to stdout, not stderr.** A probe that captured stderr saw
  nothing and compared two empty strings as equal.
- **The reliable test is positive, and the log must be checked for existence first.** With
  `-d 2 --log_file FILE`, a run that parallelized contains `r_split` / `r_merge` lines (naming the
  FIFOs and showing the fan-out width) and **no** `No region was parallelized successfully`; a run
  that fell back has the warning and no split/merge lines.
- **An absent or empty log must be treated as UNKNOWN, never as success.** `--log_file` writes
  nothing at all in some configurations (observed with `--output_optimized`), and if the target
  script does not exist, `pa.sh` segfaults in its preprocessor and writes no log. A check written
  as `grep -q "No region was parallelized" log || echo parallelized` reports success in all of
  those cases. That mistake was made and caught here; the working demo at `~/try-pash.sh` in the
  VM has the corrected form.

**Still to settle before Phase 4:** attributing a decision to a *particular command node* when a
region contains several. The region-level reading is solved (above), and the log does name the
per-node fan-out, so this is now tractable rather than open-ended. Candidates not yet tried: `--graphviz dot --graphviz_dir DIR`
(dumps the dataflow graph, most likely to give per-node detail), higher debug levels, and
`-p` captured from stdout. The study needs a per-node reading, and a region-level signal is not
enough: a region contains several commands.

### 3.4 Supplying your own annotations — use `--local-annotations-dir`, not the installed package

**PaSh supports pointing at an external annotation directory**, documented in
`docs/local-annotations-library-documentation.md` in its own repository:

```sh
$PASH_TOP/pa.sh -w 8 --local-annotations-dir /path/to/annotations script.sh
```

`pa.sh` resolves the path, exports `ANNOTATIONS_PATH`, and **prepends it to `PYTHONPATH`**
(`src/pash/pa.sh:234-238`), so `import pash_annotations` resolves there instead of in the
installed package. Verified working 2026-10-05 against a clone of `binpash/annotations`.

**This is how the study should swap arms**: one directory per arm, selected by a flag, with the
installed package never touched. It removes the need to mutate `site-packages` between runs.

**Two traps.** The flag is on `pa.sh`, the shell driver — it is **not** on the `pash` Python
entry point and does not appear in `pash --help`. And a stale `__pycache__` inside the local
directory will shadow an edit, so clear it after changing an annotation.

#### What format does that directory take?

A clone of `binpash/annotations`, i.e. a `pash_annotations/` Python package. Two layers, and only
one of them is data:

| Layer | Format | Our nine commands |
|---|---|---|
| Flag and option table — which flags exist, which take a value, which name a file | **JSON**, `pash_annotations/parser/command_flag_option_info/data/<cmd>.json`, keys `flag` and `option`. 24 commands have one. There is even an official first-draft generator, `manpage-to-json.sh`, which is `man $1 \| grep '^ -' \| … \| args-to-json.py` | `cat`, `rm`, `tail`, `tee`, `uniq`, `wc` have one; `pwd`, `sha256sum`, `tac` do not |
| Input/output info, and **parallelizability** | **Python classes only.** No data format exists | only `uniq` has a parallelizability class (§1.2) |

So: the layer Caruca's stage 1 produces (flags, which take values, which are files) has a JSON
format PaSh accepts, and PaSh's own tooling builds it from a man page — close to what Caruca
does. **The layer this study measures — parallelizability — has no data format at all.** The
adapter must emit Python.

Adding a command also needs an entry in `DICT_CMD_NAME_TO_REPRESENTATION_IN_MODULE_NAMES`
(`pash_annotations/annotation_generation/AnnotationGeneration.py`), per the annotations
repository's own README.

### 3.5 Installing and removing an annotation by hand

An annotation is a file:

```
~/pash/python_pkgs/lib/python3.12/site-packages/pash_annotations/
    annotation_generation/annotation_generators/ParallelizabilityInfoGenerator<Cmd>.py
```

Write the file to add one; delete it to remove one. **Clear `__pycache__` for that module after
either**, or the old version is reused. A command absent from
`DICT_CMD_NAME_TO_REPRESENTATION_IN_MODULE_NAMES` (`pash_annotations/config/definitions.py`) also
needs an entry there — which is the case for `pwd`, `sha256sum`, `tac` and `wc`.

The class-to-helper mapping for the adapter, confirmed against the interface:

| Caruca class | What the generator does |
|---|---|
| `stateless` | `append_to_parallelizer_list_cc_seq_conc()` and `..._rr_seq_conc()` — split, run, concatenate |
| `pure` | `append_to_parallelizer_list_cc_seq_adjf(func, is_implemented)` — needs an aggregator Caruca cannot synthesise |
| `non-pure`, `side-effectful` | append nothing |

## 5. Status of Phase 0

Settled: the annotation format and its consequences (§1), what PaSh does with an unannotated
command, the default-case question, the stock coverage of our nine commands, the pinning decision,
the VM and its safety properties, the install procedure and its one defect, and the flag surface.

**Settled 2026-10-05:**

- **It builds natively on aarch64**, including the `libdash` and `libbash` C extensions. The
  fallback plans (an x86 cloud machine, or QEMU emulation) are not needed. `pash --version` reports
  0.13.0 at commit `42a8b87`.
- **It runs and agrees with `bash`** — but see the warning below, because agreeing with `bash` turned
  out to prove less than it looks.
- **Fixed overhead is ~0.15 s per run** (0.17 s for `pash` against 0.02 s for `bash` on the same
  script, three runs each, stable). **This re-sizes the Phase 4 estimate by an order of
  magnitude:** the task document assumed ~1 s and therefore 5-10 VM-hours for Tier A. At 0.15 s,
  15,000 runs is about 40 minutes of overhead. Timing runs on larger inputs dominate instead.
- The annotation format, the install mechanism, the stock coverage, and the pinning decision — §1,
  §3.4.

**Still open:**

- **PaSh parallelizes correctly on this install.** *(An earlier version of this document said the
  opposite. That was wrong — the fault was in the test scripts, not the install. Corrected
  2026-10-05 after running PaSh's own `evaluation/intro/hello-world.sh`, which parallelizes.)*
  On `cat in.txt | grep 9 | wc -l` over 4,000,000 lines at width 8, PaSh inserts an `r_split`
  node that fans the stream into 8 FIFOs, runs **8 parallel copies of `grep`**, and merges with
  `r_merge`. Output matches `bash`.
- **A trailing `> file` redirect makes PaSh fall back to plain `bash`.** This is what caused the
  mistaken conclusion above, and it matters for the study's script design:

  | pipeline | parallelized |
  |---|---|
  | `cat in.txt \| grep 9 \| wc -l` | yes |
  | `cat in.txt \| tr … \| sort \| uniq -c` | yes |
  | `cat in.txt \| grep 9 **> out.txt**` | **no** |

  Tier A's synthesized scripts must therefore end at standard output, with the harness capturing
  it, rather than redirecting inside the script. Whether PaSh's own benchmark scripts redirect
  needs checking before Tier B is assembled — any that do would silently measure nothing.
- **A PaSh correctness bug, found 2026-10-05: it silently returns the wrong answer when it
  parallelizes a `grep` whose pattern is in double quotes.** On
  `cat in.txt | grep "\(.\).*\1…" | wc -l` over 1.3M lines: `bash` 928, PaSh **0**. *(Corrected
  2026-10-05: the trigger is single backslashes inside double quotes, as written here; an earlier
  version showed doubled backslashes, which do not trigger it. PaSh's worker command mangles the
  escaping and each worker's `grep` fails with "Invalid back reference". Reproducer:
  `scripts/pash/repro/double_quoted_grep_wrong_answer.sh`.)* The same
  regex in *single* quotes gives 928 under both. And the same double-quoted script with a trailing
  redirect — which stops PaSh parallelizing — also gives 928. So the fault is in how the parallel
  path reconstructs the command for each worker, and it is **not** annotation-related.

  **Two consequences for the study.** It is a textbook *harm* event — parallelized, wrong output —
  found on day one and caused by the consumer rather than by any annotation, which is exactly why
  task 012's exclusion gate ("drop a script if stock PaSh already disagrees with `bash`") is
  necessary: without it this bug would be charged to whichever annotation happened to be loaded.
  And it should be reported upstream.
- **Measured speedup, so the instrument is known to be able to show one.** CPU-bound workload
  (back-reference `grep` over 2.6M dictionary lines), 5 repetitions after a discarded warm-up:

  | condition | median | vs bash | efficiency |
  |---|---|---|---|
  | `bash` | 4.894 s | 1.00x | |
  | PaSh width 1 | 5.060 s | 0.97x | |
  | PaSh width 2 | 2.664 s | 1.84x | 92% |
  | PaSh width 4 | 1.494 s | 3.28x | 82% |
  | PaSh width 8 | 1.096 s | **4.47x** | 56% |

  PaSh's fixed overhead is **+0.17 s** (width 1 against `bash`), and the parallel gain is 4.62x on
  8 cores. Width 1 is the right overhead control: it runs PaSh's full split/merge machinery with
  one worker. The benchmark is `~/try-pash.sh [reps] [dict-copies]` in the VM.
- **Separately, one real compiler defect** *(did not reproduce on a 2026-10-05 re-run of
  `scripts/pash/repro/head5_pipeline.sh` at width 8 and debug levels 1 and 2: no error, correct
  answer, not parallelized; the conditions of the original failure are not recorded)*: a pipeline
  ending in `head -5` raises
  `AssertionError: assert not other_in is None` at `compiler/compilation.py:93`. Worth reporting
  upstream, and worth excluding such scripts from the corpus until it is fixed.
- **The exit gate is not met yet.** Neither demonstration succeeded: a hand-written `cat`
  annotation did not change the decision on `cat in.txt | cat > out.txt` (that region was already
  being handled), and overriding `uniq` to claim it is stateless changed neither the decision
  reading nor the output. Both failures trace to §3.3 — without a per-node decision probe there is
  nothing to observe. Settle §3.3 first, then re-run the gate.
- **The ten `oneliners` scripts against `bash`.** Not yet run; needs
  `evaluation/benchmarks/oneliners/input/setup.sh --small`, which fetches from
  `pac-n4.csail.mit.edu`.

**Do not cite Phase 0 as complete while this section still lists open items.**
